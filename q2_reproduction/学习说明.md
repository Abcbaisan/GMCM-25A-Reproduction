# 问题二：从拓扑序走到真实缓存地址

问题一主要决定“节点先后次序”；问题二还要回答“缓冲区放在哪里、空间不足时换出谁、何时换回”。这里独立实现论文可执行的调度与 SPILL 思路，修正与题目约束不符的部分。不是作者完整程序，也不包含问题三的流水线耗时优化。

## 代码和论文怎样对应

| 代码入口 | 作用 | 论文联系及实现边界 |
| --- | --- | --- |
| `MemoryPool.allocate/release` | 在一种缓存中分配连续地址，切割空闲段、合并相邻空闲段 | 落实论文算法5—7的内存管理；First-Fit/Best-Fit细节为本地补充 |
| `SpillAllocator.__init__` | 建立缓冲区属性、使用位置和五类独立缓存 | 落实缓存容量与生命周期约束；缓存 Type 保持输入值 |
| 受害者排序与 `acquire` | 当前连续块不足时选择缓冲区换出，直至可分配 | `paper-small`对应附录小尺寸优先，`paper-large`对应正文大尺寸优先；两处不一致，因此分别实验 |
| `spill_out/restore` | 生成 OUT/IN，释放和重新分配物理地址 | 对应算法7的精确 SPILL；IN 延迟到下一次使用或 FREE 之前 |
| `can_place_needed/repack` | 检查碎片是否妨碍同一操作所需缓冲区共同驻留 | 本地合法性补充；重装用真实、计费的 SPILL，不能免费移动地址 |
| `run` | 按原序列执行 ALLOC、普通操作、FREE 三类事件 | 对应算法5整体流程；普通操作所需的所有缓冲区同时受保护 |
| `save_result/main` | 输出正式三类文件、比较策略并选择合法候选 | 形成可验证的实验协议；以额外搬运量为主、次数为次 |
| `verify_q2.py` | 从正式文件独立重放，检查依赖、物理地址及成本 | 本地验证器，不调用求解器的空闲表逻辑 |
| `search_schedules.py` | DFS/释放节点优先/共享输入的蛇形输出排序 | 本地补充启发式，不是论文原算法；说明问题一低峰值不保证问题二低搬运量 |

## 先理解这四个状态

`active` 表示 ALLOC 已执行但 FREE 尚未执行；`resident` 表示此刻真正占用缓存；`pending` 表示已 OUT、等待对应 IN；`memory` 只保存最初 ALLOC 的地址。

一个缓冲区的合法路径是：

```text
ALLOC → 驻留 → SPILL_OUT → 不驻留但仍存活 → SPILL_IN → 驻留 → FREE
```

因此 `SPILL_OUT` 不等于 `FREE`。即使后面只剩 FREE，题目要求的 IN→FREE 依赖仍然有效。换回地址记录在 spill 文件中，不能修改 memory 文件来隐藏搬迁。

## 手算一个分配例子

容量为10，A占 `[0,4)`、B占 `[4,7)`，空闲 `[7,10)`。释放 A 后总空闲为7，但最大连续空闲仅4，仍无法放入大小5的 C。Best-Fit只能选择已有且足够大的洞，不能凭空把两个洞拼成一个。若换出 B，则空闲段合并成 `[0,10)`，C才有连续空间。这是教学手算，正式代码测试使用题目容量。

设第 k 次 SPILL 的缓冲区大小为 s_k，且 c_k=1 表示它被原图中某个 COPY_IN 使用，否则为0：

```text
额外搬运量 D = Σ (2 - c_k) × s_k
```

求和对象是每一次 SPILL 对，同一个缓冲区多次换出须多次计费。COPY_IN 关联缓冲区大小100，三次SPILL花费300；无COPY_IN缓冲区大小200，一次花费400。所以只比较次数可能得出相反结论。Cycles是另外的量，不加入问题二此目标。

## 怎么运行

在当前 `outputs/q2_reproduction` 目录打开 Anaconda Prompt：

```bat
conda activate FirstPythonEnv
python -m unittest discover -s . -p test_q2.py -v
python q2.py --out runs\my_baseline
python search_schedules.py --out runs\my_search
python q2.py --schedule-dir runs\my_search\input_schedules --out runs\my_optimized
python verify_q2.py --results runs\my_optimized
```

仅依赖 Python 标准库。默认读取你给定的原始ZIP和问题一结果；搬到别的电脑时用 `--zip`、`--schedule-dir` 显式指定路径。每次使用新输出目录。正式运行的环境、哈希、配置、日志和结果见学习系统项目及本目录的复现报告。

每个算例输出：`*_schedule.txt`（含新增节点的顺序）、`*_memory.txt`（初始地址）、`*_spill.txt`（各次换回地址）。`*_events.json` 是学习调试信息，验证器只读取前三类正式文件。

## 建议学习顺序与自测

1. 手算上面的连续地址例子，再读 `MemoryPool`。
2. 跟踪一个缓冲区的 active/resident/pending 状态，再读 `spill_out/restore`。
3. 理解操作为什么需要保护所有 Bufs，再读 `acquire/run`。
4. 手算两种 SPILL 成本，再检查 `_events.json` 与独立验证结果。
5. 最后读调度搜索，比较同一实例的原序列与新序列。

自测：总空闲足够为什么还会分配失败？OUT后为什么不能直接FREE？次数更少为什么成本可能更大？

参考答案依次是：连续区间不足；题目有IN→FREE约束；每次成本由大小和COPY_IN属性共同决定。学习系统将这些内容记录为有适用边界的知识；你的掌握状态保持“未评估”，待你独立解释或做题后更新。
