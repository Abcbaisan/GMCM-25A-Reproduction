## 1. 问题三到底要做什么：论文、题面、代码的共同主线

**赛题问题三（原题第 8–9 页）**：以问题一的调度顺序和问题二的内存方案为基础，在总额外搬运量“不显著增加”前提下尽量降低总运行时间；也允许联合优化。要求论文呈现六算例**时间和额外搬运量**的对比，并按附录 E 输出各算例完整的 `schedule/memory/spill` 三文件。**原题没有规定“不显著”必须为 5%**。

**优秀论文第 32–34 页（5.8、5.9 节）**将“不显著”具体化为 `δ = 0.05`，写成模型 P3：

```text
minimize T
subject to  原计算图与 SPILL 的拓扑/生命周期约束
            连续物理内存的容量和地址不重叠约束
            S(v) >= E(u), 对每条扩展依赖边 u -> v
            E(v) = S(v) + Cycles(v)
            同一 Pipe 按最终序列先后执行，不能重叠
            E(v) <= T
            C* <= (1 + δ) * C_P2, δ 通常设 0.05
```

**当前代码主链**：

```text
官方 ZIP 的 JSON + 问题二的三个结果文件
    │  read_result_files / verify_case
    ▼
solve_one：取得问题二基线、计算 base_time 与成本上限
    ├── PipelineModel.__init__：重建原图、SPILL 与物理复用依赖
    ├── PipelineModel.makespan：按依赖与 Pipe 队列推算 T
    ├── critical_order + SpillAllocator.run：换拓扑序并重新分配
    ├── improve_swaps：对某个已定地址/换出方案尝试相邻操作交换
    └── consider：验证 → 成本门槛 → 估时 → 选候选
    ▼
save_three：正式三文件；main：report.json
```

代码是**“候选枚举 + 独立验证 + T 优先选优”**的工程替代方案，既没有直接求解论文 P3 的完整 MILP，也没有完整实现论文算法 10–12 的动态反馈循环。

## 3. 把 P3 公式逐条展开为代码操作

### 3.1 时间公式：论文算法 13 ↔ `makespan`

令 `preds[v]` 表示所有显式扩展依赖前驱，`pipe_finish[p]` 为相同流水单元前一个节点的完成时刻，则代码递推为：

```python
ready_by_dependencies = max((finish[u] for u in self.preds[v]), default=0)
start = max(ready_by_dependencies, pipe_finish[pipe]) if pipe else ready_by_dependencies
end = start + self.cycles[v]
finish[v] = end
# T = max_v finish[v]
```

- 论文 PDF **第 33 页**的 `S(v_i)≥E(v_s)` 对应 `dep_end`；同 Pipe 顺序约束对应 `pipe_finish`；第 **38 页算法 13**的 `end=start+cycles`、`total_time=max(end)` 对应 `makespan`。
- 原始操作的 `Pipe/Cycles` 从官方 JSON 读取。ALLOC/FREE 在 `cycles` 列表中默认 0、`pipe=None`，只施加依赖，不占用计算流水。
- 扩展依赖由 `edge(u,v)` 加入：原图边、SPILL 基本边、已/未使用的 SPILL 前后边、多次 SPILL 衔接及物理地址复用边。
- `last_release[t][offset:offset+size]` 每地址记录上次释放节点；重新申请同一地址时添加旧释放→新申请边。若前次释放是 SPILL_OUT 或本次申请是 SPILL_IN，代码也能处理，回应**题面附录 C 关于 SPILL 复用“自行思考”**的要求。
- **准确边界**：模型是抽象调度周期模拟，不是硬件实测；论文算法 13 写到的独立 `cache_wait` 数值项没有单独实现，相关等待通过依赖链传递。

### 3.2 搬运公式：论文 P3/P2 ↔ `verify_case` 与预算门槛

```text
每次 SPILL 若目标 buf 在原图某个 COPY_IN.Bufs 中：cost = Size(buf)
否则：cost = 2 * Size(buf)
C = 所有 SPILL pair cost 之和
C <= baseline_C * (1 + tolerance_pct / 100)
```

- 成本在 `../q2_reproduction/verify_q2.py::verify_case` 对 `spills` 清单重新计算，而非只相信 `q2.py::SpillAllocator.extra`。
- `solve_one` 先检查基线，再在 `consider` 中对每个候选重新 `verify_case`；不满足预算直接拒绝。最后输出前再检查一次。
- **论文 5.9 的 `C_P2`**表示该论文问题二口径；代码中的 `baseline_C` 是仓库内指定的 `q2-20260914/optimized` 三文件所形成的成本。即使两者都是 5%，**基线数值不同，不能据此直接比较 T 或 5% 阈值**。

### 3.3 候选生成与重新分配：论文算法 10–12 ↔ `solve_one`

代码逐层做：①读已验证的 q2 baseline；②读取另一份历史 q2 results；③抽取 baseline 的原节点拓扑序；④运行 `critical_order` 的关键路径 / FREE 优先两种原图序；⑤对序列试 `farthest/cost-distance` 和若干 `best-fit/first-fit` 组合，通过 `SpillAllocator.run` **重新生成完整地址/SPILL**；⑥验证和评估；⑦对当时最优方案做相邻普通操作交换。`consider` 按 `(time, movement, len(spills))` 字典序比较，时间优先，其次搬运，最后 SPILL 对数。论文算法 12 则写的是多轮 `T + μ(C−baseline)` 加权适应度；**二者不是同一个目标函数**。

## 4. 最重要的差异、风险与可改进方向

1. **算法 10 尚未完整复现**：`critical_order` 的优先级是静态反向最长**周期**路径与可选 FREE 优先；没有动态统计 `pipe_finish`、就绪节点的预估空闲时间和负载惩罚。因此“有 critical_order”不等于“有论文的自适应负载均衡调度”。
2. **算法 11 尚未完整复现**：项目的 `MemoryPool` 实现常规连续空间 Best-Fit 和释放合并；没有把未来完成时刻/地址复用等待纳入分配代价。论文第 36 页伪代码的 `allocation=0` 仅是“临时分配失败处理”行，也不能当作一个合法物理分配方案；项目必须通过 SPILL 或拒绝不可行方案。
3. **算法 12 属于不同求解框架**：论文多轮迭代与 `μ` fitness、文中 2-opt；项目是固定有限候选+字典序，不维护 Pareto 前沿，不求全局最优，也未实现作者每 20 轮局部搜索。
4. **相邻跨 Pipe 交换的数学局限（纠正此前代码说明）**：在当前 `PipelineModel` 中，若只交换相邻且相互独立的**不同 Pipe**普通节点，且地址、SPILL、依赖及各 Pipe 内部节点顺序均不变，则 `preds` 和每条 Pipe FIFO 序列完全不变，因而 `makespan` **必定不变**。真正可能影响现有模型时间的是**同 Pipe 独立操作的换序**，或更大规模地更换拓扑序、改变地址复用/SPILL 依赖。因此不能以“允许跨 Pipe 交换”本身作为已经提升并行性的依据。代码的 `improve_swaps` 当前也允许同 Pipe 交换；只有实测 `time` 改善且验证通过才可声称有效。
5. **算例专项策略只存在论文叙述中**：第 32–33 页提出 Matmul 对角优先、FA 阶段交织、Conv 自适应广度。当前代码没有根据附录 F 的分块/层信息识别并执行这些专门规则；可把它们列为下一阶段工作，而非现有成果。
6. **`README.md` 的局部搜索文字已落后于 `q3.py`**：README 仍描述“相邻、同 Pipe、不同缓冲区”限制，现行代码允许不同 Pipe、也没有显式缓冲区不相交过滤。以代码和本对照文档为当前行为准，后续修改 README 时应同步。
7. **可行性不等于论文数值复现**：`verify_case` 能检查图依赖、生命周期、容量、地址区间及搬运模型；`makespan` 进一步估算时间。它们不能替代论文完整算法，也不验证张量内容语义或硬件实际运行时间。
